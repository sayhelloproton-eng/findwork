# 岗位评估｜通用判断流程

本文件只负责岗位决策流程，不存储、复述或扩张个人偏好与黑名单。私有个人画像、求职偏好（倾向）和排除条件的输入以 private-policy.md 所定义的三项本地文件为准。先完成真实采集、入库和去重，再选择需要评估的岗位。

## 按顺序判断

1. 核对三项私有策略有效。必要策略缺失、互相矛盾且尚不能从最新用户确认消解时，不写 WORTH/PASS，不执行对外操作。
2. 先核实是否**有证据命中明确批准的硬排除**。仅有事实支撑才能 PASS，并写规则与证据；不能自行新增排除公司或因一般不确定性 PASS。
3. 未命中时，以岗位实际核心开发工作、真实职业能力与合理迁移判断能否胜任；有积极依据才 WORTH。无硬排除不意味着无条件 WORTH。
4. 行业、职级、招聘活跃、现实待遇及私有倾向用于对 WORTH 排优先级，不拿优先级低当 PASS 或 PENDING。
5. 猎头、外包、代理、混合招聘、客户/部门/用工关系不明与需要私聊，若已能确认存在匹配的真实工程职位，则不单独阻塞 WORTH。优先 AI 自己检索/分析可用岗位资料，而非把普通沟通细节交由用户确认。
6. 职位关闭、历史联系和平台执行资格与适配性判断分开，不能用「现在不可联系」代替 PASS。

## 三态判定

| 状态 | 必备证据 |
|---|---|
| WORTH | 实际开发职责能由已有经验承担或合理迁移，未命中已确认硬排除，记录正向匹配理由 |
| PASS | 明确命中已确认硬排除，或岗位核心工作已证实完全不符合个人已确认求职目标，记录具体事实 |
| PENDING | 尚未启动评估、真正缺决定性事实或必要策略、AI 已主动查证仍不能可靠区分 WORTH 与 PASS，记录具体关键缺口与下一步自主调研 |

内部 NEED_DETAIL 只在 List 无法提供决定性信息且需要补真实 JD 时使用，用户界面仍归 PENDING。AI 主动写回的 PENDING 必须附理由（reason），写明已知证据、仍有的决定性疑问以及 AI 自行查证的下一步建议；非决定性偏好疑问与后续联系细节不能被当作决定性事实。仅当新规则需要用户授权时才请求用户决策。

## 数据安全和动作边界

只处理需要复核的 PENDING/NEED_DETAIL；已有 WORTH/PASS 默认保留（但新规则审计或用户明确授权的复评可使用最新 source hash 和 revision 进行更新），不得因重复采集自动翻转判断。来源变化决策 stale 必须先核对，不得直接 SQL 修改状态。
使用 references/database.md 规定的 decide-ai 输入 jobId、status、reason、strategyVersion、expectedRevision、expectedSourceHash，写入后再次 get 核验。
WORTH 只允许进入候选列表，不是发送授权。任何 Greet/投递必须有岗位级明确授权，并在真实发送前核验最新 WORTH、未过期、无历史阻断；回执需真实落盘，不能重发未知或已成功动作。
