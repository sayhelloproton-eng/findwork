# 岗位评估｜通用规则与状态机

本文件不存储个人策略；三项私有输入见 `private-policy.md`。**必须先完成入库和去重，再使用当前数据库状态选择评估对象。**

## 三个维度必须同时考虑

1. **个人画像**：判断用户能否完成 JD 的核心职责。拆分已证明的直接经历、合理可迁移的能力、目前不确定的能力和真正不可满足的关键条件；不简单数前端/AI/后端关键词。
2. **求职偏好**：岗位工作性质、技术方向、行业、现实因素是否符合用户喜好。偏好用于 WORTH 候选排序，不自动转换成硬性排除，除非用户明确确认它是“绝对不投”。
3. **排除条件**：先检查已确认的拒投类别和不可接受条件。只有事实明确、证据充分、命中规则才能 PASS，并记录命中依据和原因；未知不凭空淘汰。

若任一策略尚未确认或无法读取：**不输出正式 WORTH/PASS 决策、不调用 decide-ai**。可以导入事实、查看岗位和请求补充私人策略；不擅自把缺失值当默认值。

## 新旧记录分流

- 仅从 DB 的 `PENDING` 行评估。查询 `status=PENDING` 会同时包含内部 `NEED_DETAIL`，对缺真实 JD 且影响判断的职位先补 Detail。
- 已有 `WORTH/PASS` 或已联系岗位，不因每次重新采集/导入而自动重新评估；原始历史决策保留。同 ID 的新 List 可能产生 `LIST_UPDATED`，不能当新职位。
- `decision_stale` 说明来源与保存判断不一致，旧 WORTH 不可直接沟通；只有用户明确要求/授权复核时才能用新 hash、revision 重评并写入。已经沟通或真实申请过的绝不自动重发。
- 新补齐 Detail 后，之前的内部 NEED_DETAIL 会按 DB 设计回到 PENDING，可继续评估。

## 判断与落库

| 状态 | 合同 |
|---|---|
| PENDING | 未完成评估、缺策略/关键事实或冲突未决 |
| NEED_DETAIL | 缺少足够 Detail，优先完成采集；属于内部待评估，不是“拒投” |
| WORTH | 未触发已确认硬排除，工作可胜任或合理迁移，值得争取；**必须写具体原因** |
| PASS | 明确命中已确认的排除规则或不能满足的关键硬要求；**必须写具体原因和证据** |

对 WORTH/PASS 使用 `npm run jobs -- get JOB_ID` 获取 `revision` 和 `decision_basis.hash`，按 `references/database.md` 的 `decide-ai` 输入 `jobId,status,reason,strategyVersion,expectedRevision,expectedSourceHash`，返回后再次 `get` 验证写入。未完成对照不能猜测理由。来源变化/版本冲突时先重新读取，不越过乐观锁。不要直接 SQL 改判断列。

## 决策后动作

WORTH 只是“可联系候选”，不代表用户已授权发送。按能力匹配、活跃证据、行业正向偏好与其他真实条件排序，交给用户确认具体岗位，然后 `claim → 平台 Greet → import-greet → get`，只有真实回执 SUCCESS 才记已沟通。已沟通、失败、IN_FLIGHT/UNKNOWN 均不得盲目重复发送。

Greet 不等于投递简历；投递后聊天、反馈及面试跟进不由本平台接管。
